# Lab 1 - git/dvc and data preparation

## Question 1
**Observe the files created by `uv init`, what do you think they contain?**

- `.python-version` — pins the Python version the project uses, so `uv` always runs the project with a consistent interpreter regardless of what's installed system-wide.
- `pyproject.toml` — the project manifest: name, version, Python version requirement, and (as dependencies are added via `uv add`) the dependencies list. This is the modern replacement for `requirements.txt` + `setup.py`.
- `README.md` — empty placeholder for project documentation.
- `src/` — scaffold folder for the project's source code.

`uv init` does not create a virtual environment or lockfile immediately — those are created lazily, the first time `uv run` or `uv add` is used.

## Question 2
**What are the created files (from `dvc init`)? What are they used for? Which ones should be pushed to git?**

- `.dvc/config` — DVC's main configuration file (remote URLs, settings). Starts empty until a remote is added. **Pushed to git** (contains no secrets).
- `.dvc/.gitignore` — auto-generated by DVC to make git ignore DVC's internal cache/tmp folders. **Pushed to git.**
- `.dvc/tmp/` — DVC's internal scratch space (locks, state, logs). **Not pushed** — excluded via `.dvc/.gitignore`.
- `.dvcignore` (repo root) — tells DVC which files/folders to ignore when scanning for trackable content, analogous to `.gitignore`. **Pushed to git.**

Everything except `.dvc/tmp/` (and later `.dvc/cache/`) is committed to git — DVC only ever tracks lightweight metadata/config in git, never actual data or its own cache.

## Question 3
**Where are the credentials stored? What are the options other than `--global`? Should credentials be pushed to github?**

- Credentials set with `--local` are stored in `.dvc/config.local`, a per-repo file that DVC's own `.gitignore` excludes from git by default.
- Credentials set with `--global` are stored in DVC's global config in the user's home directory (applies to all repos on that machine, not just this one).
- Other option: no flag at all writes to the plain (repo-level, committed) `.dvc/config` — this should be **avoided** for secrets.
- **Credentials should never be pushed to GitHub.** Using `--local` (or `--global`) instead of the default keeps secrets out of the version-controlled config file.

## Question 4
**Take a look at the .gitignore file. Explain what happened.**

Running `dvc add data` automatically added `/data` to `.gitignore`. This tells git to ignore the entire `data/` folder, so the actual image files are never committed to the git repository. DVC takes ownership of tracking the data — git only tracks the lightweight `data.dvc` pointer file instead.

## Question 5
**Do you see a .dvc file? What does it contain?**

Yes, `data.dvc` was created. It contains:

```yaml
outs:
- md5: 94afad23dc86ad238cbb965ec28aecd4.dir
  size: 1274882585
  nfiles: 36578
  hash: md5
  path: data
```

- `md5` — the hash of the directory manifest (a fingerprint of all files and their contents)
- `size` — total size of the tracked data in bytes
- `nfiles` — number of files tracked
- `path` — the local folder being tracked (`data/`)

This is a lightweight pointer file committed to git. It lets DVC know exactly which version of the data corresponds to this git commit, without storing any actual image data in git.

## Question 6
**Check your main branch on the GitHub web UI. Is the code there? Is the data there? Do you have any file that points to the data location? And what about DagsHub web UI, do you see the data?**

- **GitHub** — the code is there (scripts, config files, `pyproject.toml`, etc.). The actual data (images) is **not** there — git ignores the `data/` folder.
- **Pointer file** — `data.dvc` is visible on GitHub. It acts as the reference that links this git commit to the corresponding data version stored on DagsHub.
- **DagsHub** — the actual image files are stored there and visible under the Data tab. DagsHub serves as the DVC remote storage for the dataset.

## Question 7
**In a completely new temporary folder clone your GitHub repo. Do you see the data folder? What DVC command is needed to get the data folder?**

After cloning, the `data/` folder is **not present** — git only cloned the code and the `data.dvc` pointer file, not the actual images. To download the data from DagsHub, you need to run:

```bash
dvc pull
```

This reads `data.dvc`, connects to the configured DVC remote (DagsHub), and downloads the correct version of the dataset.

## Question 8
**Do you still see the new folders you created? food11_processed and food11_processed_mini?**

No. After running `git checkout <old-commit-hash>` and `dvc checkout`, only `food11_raw` is present in the `data/` folder. The `food11_processed` and `food11_processed_mini` folders are gone because the `data.dvc` at that older commit only pointed to the raw dataset. DVC restored the data directory to exactly match that earlier version.

This demonstrates the core value of git + dvc together: not only is the code versioned, but the data is versioned alongside it. Checking out any past commit gives you both the correct code **and** the correct data for that point in time.
